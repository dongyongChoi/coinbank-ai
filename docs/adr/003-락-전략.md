# ADR 003. 동시 송금에서 계좌를 어떤 락으로 보호할 것인가

- 상태: 채택됨 (기본값 비관 락)
- 날짜: 2026-11-18

## 맥락
M1의 송금은 락이 없었다. 같은 계좌에서 1,000원씩 100건을 동시에 보내자 송금 기록은 100건인데 잔액은 10건만 빠졌다(갱신 유실). 두 트랜잭션이 같은 잔액을 읽고 각자 덮어썼기 때문이다.

송금은 두 계좌를 함께 바꾼다. 그래서 갱신 유실과 함께 데드락도 막아야 한다. A→B와 B→A가 동시에 오면 서로가 잡은 계좌를 기다릴 수 있다.

## 선택지
세 방식 모두 구현했고 `coinbank.lock-strategy` 설정으로 바꿀 수 있다. 세 방식 모두 두 계좌를 계좌 번호 순서로 잠가 데드락을 피한다.

### A. 비관 락 (`pessimistic`)
`SELECT ... FOR UPDATE`로 읽어 행을 잠근다. 다른 트랜잭션은 커밋될 때까지 기다린다.
- 장점: 충돌이 나면 기다릴 뿐 다시 하지 않는다. 코드가 단순하다.
- 단점: 기다리는 동안 DB 커넥션을 쥐고 있다. DB가 여러 대로 나뉘면 쓸 수 없다.

### B. 낙관 락 (`optimistic`)
잠그지 않고 읽고, 저장할 때 `@Version`으로 그사이 바뀌었는지 확인한다. 바뀌었으면 새 트랜잭션으로 다시 시도한다(최대 100번, 1~20ms 무작위 대기).
- 장점: 충돌이 드물면 기다림이 없다.
- 단점: 충돌이 잦으면 재시도가 쌓여 느려진다. 재시도 상한을 넘으면 요청이 실패한다(409).

### C. Redis 분산 락 (`redis`)
트랜잭션을 열기 전에 Redisson으로 계좌별 Redis 락을 잡고, 커밋이 끝난 뒤에 푼다.
- 장점: DB 밖에서 잠그므로 서버나 DB가 여러 대여도 통한다. 기다리는 동안 DB 커넥션을 쥐지 않는다.
- 단점: Redis라는 의존이 하나 늘고, 요청마다 Redis를 오간다. 락을 트랜잭션 안에서 잡으면 커밋 전에 풀려 갱신 유실이 다시 생긴다(실험에서 송금 200건 중 약 200번의 version 충돌로 확인).

## 측정 결과
조건: 송금 1만 건, k6 가상 사용자 50명, 계좌 100개(요청이 흩어짐)와 2개(한 계좌 쌍에 몰림). 요청의 약 5%는 같은 `Idempotency-Key`로 한 번 더 보냈다. 측정마다 DB를 비우고, 1,000건으로 워밍업한 뒤 측정했다. 앱 1대, MySQL 1대, Redis 1대 모두 로컬(Apple M2 Pro, 12코어, 32GB). 조건마다 한 번씩 돌렸다.

| 전략 | 계좌 수 | TPS | 평균 | p95 | p99 | 최대 | 실패 |
|---|---|---|---|---|---|---|---|
| 비관 락 | 100 | 871 | 52.6ms | 103.1ms | 140.8ms | 251ms | 0 |
| 낙관 락 | 100 | 803 | 57.8ms | 126.1ms | 174.2ms | 305ms | 0 |
| Redis 분산 락 | 100 | 734 | 64.4ms | 143.4ms | 222.1ms | 433ms | 0 |
| 비관 락 | 2 | 360 | 135.1ms | 249.4ms | 336.3ms | 619ms | 0 |
| 낙관 락 | 2 | 139 | 357.2ms | 1,090.0ms | 1,719.1ms | 3,192ms | 0 |
| Redis 분산 락 | 2 | 218 | 228.2ms | 242.6ms | 253.7ms | 263ms | 0 |

- TPS는 초당 처리한 송금 건수(재전송 포함 반복 수)다. 응답 시간은 송금 요청(`POST /transfers`)만 잰 값이다.
- 정합성은 여섯 번 모두 같았다. 송금 기록 10,000건, 중복 Idempotency-Key 0건, 원장 합산과 잔액이 다른 계좌 0개, 합이 0이 아닌 거래 0건, 전체 잔액 합 일치, 재전송 약 500건 모두 같은 송금 번호.

읽은 것:
- 요청이 흩어지면 세 방식의 차이는 10~20% 안쪽이다. 비관 락이 가장 빠르다.
- 한 계좌 쌍에 몰리면 차이가 커진다. 낙관 락은 TPS가 비관 락의 39%로 떨어지고 p95가 1초를 넘는다. 재시도가 쌓이기 때문이다.
- Redis 분산 락은 몰릴 때 평균은 비관 락보다 느리지만 p95와 최대값이 가장 고르다(p95 242.6ms, 최대 263ms).

## 결정
기본값을 비관 락(`pessimistic`)으로 둔다. 낙관 락과 Redis 분산 락은 비교와 이후 실험을 위해 설정으로 남겨 둔다.

## 결정 이유
(Claude Code가 측정 결과를 바탕으로 작성했다.)

비관 락은 요청이 흩어질 때와 한 계좌에 몰릴 때 모두 TPS가 가장 높았다. 송금은 같은 계좌에 요청이 겹치는 일이 드물지 않고(월급날, 이벤트), 그때 기다리기만 할 뿐 다시 하지 않는 방식이 가장 안정적이었다. 지금은 앱과 DB가 한 대씩이라 DB 행 락만으로 충분하다.

낙관 락은 요청이 흩어질 때는 비관 락과 비슷했지만, 몰릴 때 TPS가 39%로 떨어지고 p95가 1초를 넘었다. 재시도 상한을 넘으면 요청이 실패하는 위험도 있다. 충돌이 드문 데이터에 맞는 방식이라 송금의 기본값으로 고르지 않았다.

Redis 분산 락은 몰릴 때 응답 시간이 가장 고르게 나왔지만, 두 조건 모두 TPS가 비관 락보다 낮았다. 요청마다 Redis를 오가는 비용이 붙고, 장점인 "서버 여러 대"는 지금 구조에서 쓸 일이 없다. 앱을 여러 대로 늘리거나 DB 밖의 자원을 잠가야 할 때 다시 본다.

## 측정의 한계
- 조건마다 한 번씩만 돌렸다. 몇 %의 차이는 실행마다 달라질 수 있다.
- 앱, DB, Redis, k6가 모두 한 컴퓨터에 있다. k6는 컨테이너에서 호스트의 앱을 부른다.
- 앱이 1대라 분산 락의 장점(여러 서버)은 측정하지 못했다.
- 낙관 락의 재시도 횟수는 부하 테스트에서 따로 세지 않았다. 테스트(한 계좌 쌍에 100건)에서는 송금 한 건당 평균 약 7번이었다.

## 다시 재기
```
docker compose up -d
./k6/bench-locks.sh build/bench
```
결과는 `build/bench/`에 전략·조건별 k6 요약(`*.json`)과 DB 정합성 검사(`*.db`)로 남는다.

## 후속
- M3: 특판 적금은 한 상품에 요청이 몰리는 구조라, 이 측정의 "계좌 2개" 조건과 비슷하다. 한도 차감 방식을 정할 때 이 결과를 참고한다.
- 낙관 락의 `MAX_ATTEMPTS`(100)는 지금 측정에서 실패 0건을 보장했지만 실제 서비스 값으로는 크다. 낙관 락을 쓰게 되면 다시 정한다.
