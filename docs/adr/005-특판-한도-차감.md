# ADR 005. 선착순 특판의 한도를 어디서 어떻게 차감할 것인가

- 상태: 채택됨 (Redis Lua 조건부 차감)
- 날짜: 2026-11-24

## 맥락
특판 적금은 문이 열리는 순간 한 상품에 가입이 한꺼번에 몰리고, 대부분은 마감으로 돌아간다. 한도보다 많이 개설되면 안 된다.

M3-1의 첫 구현은 "가입 수 세기 → 한도와 비교 → 가입 기록"을 잠금 없이 했다. 세는 것과 넣는 것 사이에 다른 요청이 끼어들어, 한도 10개 상품 10개에 각각 100명이 동시에 가입하면 상품 4~5개가 11개로 초과 개설됐다(테스트 3번 모두). 상품 1개로는 10번 중 4번만 재현돼서, 몰림을 상품 10개에 반복하는 테스트로 바꿨다.

## 선택지
### A. Redis Lua 스크립트로 조건부 차감 (채택)
상품마다 남은 자리를 Redis 숫자 하나(`product:{id}:remaining`)로 둔다. "남은 자리 확인 → 0보다 크면 1 빼기"를 Lua 스크립트 하나로 실행한다. Redis는 스크립트 하나를 끝까지 실행한 뒤 다음 명령을 받으므로 사이에 끼어들 수 없다.
- 장점: 메모리에서 바로 답한다. 마감될 요청은 DB에 가지 않고 돌아간다. DB에는 자리를 받은 요청만 들어온다.
- 단점: 기록하는 곳이 Redis와 MySQL 두 군데가 되어 어긋날 수 있다(아래 "대가").

### B. DB 조건부 UPDATE
`UPDATE savings_product SET remaining = remaining - 1 WHERE id = ? AND remaining > 0`. 바뀐 행이 1이면 자리를 받은 것이다.
- 장점: 저장소가 MySQL 하나라 어긋날 일이 없다. 가입 기록과 같은 트랜잭션에 넣을 수 있다.
- 단점: 마감될 요청까지 모두 같은 행 앞에 줄을 서고, 기다리는 동안 DB 커넥션을 쥔다. 커넥션 풀(10개)을 송금과 나눠 쓴다.

### C. DB 비관 락
상품 행을 `SELECT ... FOR UPDATE`로 잠그고 세고 넣는다. B와 같은 단점에 더해 트랜잭션이 길다.

### 고르지 않은 변형: Redis `DECR`만 쓰고 음수면 거절
더 짧지만 마감 뒤에도 숫자가 계속 내려간다(-1, -2, …). 실패한 가입의 자리를 돌려줄 때(+1) 음수에서 1 오를 뿐이라 돌려준 자리를 아무도 쓰지 못한다.

## 측정 결과
조건: 계좌 2,000개가 한도 100인 상품 하나에 한 번씩 가입(k6 가상 사용자 200명, 모두 동시에 출발). 매번 DB와 Redis를 비우고, 작은 부하(200명, 한도 10)로 워밍업한 뒤 같은 조건을 3번 쟀다. 앱 1대, MySQL·Redis·Kafka·k6 모두 로컬(Apple M2 Pro, 12코어, 32GB).

| 회차 | 가입(201) | 마감(409) | 연결 실패 | 전체 p95 | 가입 p95 | 마감 p95 | 최대 |
|---|---|---|---|---|---|---|---|
| 1 | 100 | 1,900 | 0 | 369.9ms | 386.8ms | 369.8ms | 782ms |
| 2 | 100 | 1,898 | 2 | 322.0ms | 302.9ms | 323.0ms | 736ms |
| 3 | 100 | 1,898 | 2 | 304.7ms | 315.6ms | 303.7ms | 1,115ms |

- 세 번 모두 끝난 뒤 DB 가입 기록 100건, Redis 남은 자리 0, 못 보낸 가입 이벤트 0건, 알림이 된 가입 이벤트 100건.
- 응답 시간은 가입 요청(`POST /products/{id}/subscriptions`)만 잰 값이다. 최대값은 앱이 응답한 요청 중 가장 느린 것이다.
- 2·3회차의 "연결 실패" 각 2건은 앱에 닿기 전에 `dial: i/o timeout`(30초)으로 끝났다. 200명이 동시에 연결을 열 때 서버의 연결 대기 줄이 넘친 것으로 추정한다(확인하지 않음). 앱에 도착하지 않아 정합성에는 영향이 없다. 이 30초 때문에 2·3회차의 전체 시간이 늘어나 처리량(TPS)은 비교에 쓰지 않았다.
- 마감 응답(409)도 가입(201)과 응답 시간이 비슷하다. 마감 요청도 계좌 확인과 상품 조회는 DB에서 한다(`ProductService.subscribe`).

## 결정
선착순 한도는 Redis Lua 조건부 차감(A)으로 지킨다.

## 결정 이유
(Claude Code가 측정 결과와 사용자의 판단 "수천 명이 몰리는 것을 생각해서"를 바탕으로 작성했다.)

특판은 문이 열리는 순간 수천 명이 몰리고, 그중 대부분은 마감으로 돌아갈 요청이다. 이 상황에서 중요한 것은 "자리를 받지 못할 요청을 얼마나 싸게 돌려보내느냐"다. A는 남은 자리 확인과 차감을 메모리에서 한 번에 끝내므로, 마감될 요청이 DB 행 앞에 줄을 서지 않고 DB 커넥션도 쥐지 않는다. DB에는 자리를 받은 100건만 들어간다. 측정에서 2,000명이 동시에 몰려도 세 번 모두 정확히 100건만 개설됐고 p95는 400ms 아래였다.

B(DB 조건부 UPDATE)는 저장소가 하나라 어긋날 걱정이 없다는 점에서 더 단순하다. 하지만 마감될 1,900건까지 같은 상품 행의 잠금을 기다리며 커넥션 10개를 송금과 나눠 쓴다. ADR 003에서 한 계좌에 몰릴 때 비관 락도 줄을 서며 느려졌던 것과 같은 모양이다. C는 B보다 트랜잭션이 길어 더 불리하다. 다만 B·C는 재지 않았으므로 이 판단은 추론이다(아래 "측정의 한계").

A의 대가인 "Redis와 MySQL이 어긋날 수 있다"는 자리 돌려주기(M3-3)와 `QuotaAudit`으로 감당할 수 있다고 봤다. 흔한 실패(DB 저장 실패)는 자리를 돌려줘 맞춘다. 남은 구멍은 "커밋은 됐는데 응답만 끊긴" 드문 경우로, 자리가 하나 늘어 한도보다 1건 더 개설될 수 있다. 이것은 막지 못하고 `QuotaAudit`이 찾아낸다. 특판 한 번에 1건 초과가 드물게 생길 위험과, 몰림마다 DB 커넥션이 묶이는 위험을 비교해 앞의 것을 받아들였다.

## 대가와 대응
- DB 저장이 실패하면 가져간 자리를 돌려준다(`ProductQuota.release`, 숫자가 있을 때만 +1). 트랜잭션은 가입 기록 부분에만 걸어 커밋 결과를 보고 돌려줄지 정한다(M3-3).
- 커밋은 됐는데 응답만 끊긴 드문 경우에는 자리를 잘못 돌려줘 하나가 늘어난다. 막지 못하고 `QuotaAudit`("Redis 남은 자리 = 한도 - 가입 기록 수")이 찾아낸다.
- Redis가 숫자를 잃으면 가입이 오류로 끝난다. 가입 기록으로 다시 채우는 일은 아직 없다.

## 측정의 한계
- B·C는 구현하지도 재지도 않았다. "마감될 요청까지 DB에 줄을 선다"는 B·C의 단점은 측정이 아니라 추론이다.
- 마감 요청도 계좌·상품 조회로 DB를 두 번 쓴다. 한도가 찬 뒤에는 이 조회 없이 바로 거절하면 DB 부담을 더 줄일 수 있다(재지 않음).
- 조건마다 3번 쟀다. 앱 1대라 Redis를 여러 서버가 함께 쓰는 상황은 재지 않았다.
