# ADR 004. 멱등 키를 어디에 저장할 것인가

- 상태: 채택됨
- 날짜: 2026-11-18

## 맥락
클라이언트는 응답을 못 받으면 같은 송금 요청을 다시 보낸다. 응답 유실, 타임아웃, 버튼 연타, 게이트웨이의 자동 재시도가 그 경로다. 서버가 이를 새 송금으로 처리하면 돈이 두 번 빠진다. 락(ADR 003)은 잔액 계산이 틀리는 것을 막을 뿐, 같은 송금이 두 번 처리되는 것은 막지 못한다.

그래서 `POST /transfers`는 `Idempotency-Key` 헤더를 필수로 받는다. 클라이언트가 송금마다 키를 한 번 만들고, 재전송할 때는 같은 키를 쓴다. 서버는 같은 키를 한 번만 처리하고, 다시 오면 처음 결과를 돌려준다. 문제는 "이 키를 이미 처리했는가"를 어디에 기록하느냐다.

## 선택지
### A. 송금 테이블의 컬럼 + 유니크 제약 (MySQL)
`transfer.idempotency_key`에 유니크 제약을 건다. 송금 기록과 키가 같은 행, 같은 트랜잭션에 들어간다.
- 장점: 송금이 커밋되면 키도 커밋되고, 롤백되면 키도 사라진다. 둘이 어긋날 수 없다. 동시에 온 같은 키는 DB가 막는다.
- 단점: 키가 송금 테이블에 영원히 남는다. 키 조회가 송금 요청마다 DB를 한 번 더 읽는다.

### B. Redis에 키 저장 (SETNX + 만료 시간)
요청이 오면 Redis에 키를 먼저 넣고, 이미 있으면 중복으로 본다.
- 장점: 빠르다. 만료 시간을 줘서 오래된 키가 저절로 지워진다.
- 단점: Redis와 MySQL을 한 트랜잭션으로 묶을 수 없다. 키를 넣은 뒤 송금이 롤백되면 키만 남아 정상 재시도를 막고, 송금 커밋 뒤 키 기록이 실패하면 중복을 못 막는다. 결과(송금 번호)를 돌려주려면 Redis에 응답도 따로 저장해야 한다.

### C. 별도 멱등 키 테이블 (MySQL)
`idempotency_key(key, request_hash, response, created_at)` 같은 테이블을 따로 둔다.
- 장점: 송금 말고 다른 API(M3의 적금 개설)에도 같은 방식을 쓸 수 있다. 오래된 키를 정리하기 쉽다.
- 단점: 테이블과 코드가 하나 더 늘어난다. 지금은 멱등 처리가 필요한 API가 송금 하나뿐이다.

## 결정
A를 채택했다.
- 처리 순서: 먼저 키로 끝난 송금을 찾고, 있으면 그 결과를 돌려준다. 없으면 송금 기록을 먼저 INSERT하고 돈을 옮긴다.
- 같은 키가 동시에 오면 유니크 제약이 뒤의 INSERT를 막는다(`DataIntegrityViolationException`). 그 요청은 먼저 끝난 송금의 결과를 돌려받는다.
- 같은 키인데 계좌나 금액이 다르면 400으로 거절한다.
- 실패한 송금(잔액 부족 등)은 롤백되어 키도 남지 않는다. 같은 키로 다시 보내면 처음부터 다시 처리된다.

## 결정 이유
(Claude Code가 작성했다.)

멱등 키는 "이 송금이 이미 처리됐는가"의 기록이라, 송금 기록과 어긋나면 안 된다. A는 키가 송금 기록과 같은 행, 같은 트랜잭션에 들어가므로 송금이 커밋되면 키도 남고 롤백되면 키도 사라진다. 동시에 온 같은 키도 DB의 유니크 제약이 막아 줘서 별도의 락이 필요 없다.

B(Redis)는 빠르지만 MySQL 트랜잭션과 묶을 수 없다. 키만 남거나 송금만 남는 경우를 따로 처리해야 하고, 그 처리가 틀리면 돈이 두 번 빠진다. 속도를 얻으려고 정합성을 맡길 이유가 지금은 없다.

C(별도 테이블)는 여러 API에 쓰기 좋지만, 지금 멱등 처리가 필요한 API는 송금 하나뿐이다. M3에서 적금 개설에도 필요해지면 그때 옮긴다.

## 확인한 것
- 같은 키로 20번을 동시에 보내면 송금은 1건이고 20번 모두 같은 송금 번호를 받는다. 세 락 전략 모두 통과했다.
- 이때 비관 락에서 20번 중 15번이 유니크 제약에 걸려 돌아왔다. 유니크 제약을 빼고 돌리면 같은 키의 송금이 여러 줄 들어가 테스트가 실패했다. 먼저 조회하는 것만으로는 동시 요청을 못 막는다.
- k6 부하 테스트(ADR 003)에서 송금 1만 건을 6번 돌리며 매번 약 500건(약 5%)을 같은 키로 재전송했다. 재전송은 모두 같은 송금 번호를 받았고, 끝난 뒤 DB의 송금 기록은 매번 10,000건, 중복 키는 0건이었다.

## 후속
- M3: 특판 적금 개설에도 멱등 처리가 필요해지면 C(별도 테이블)로 옮길지 다시 본다.
- 키가 쌓이는 양과 보관 기간은 지금 다루지 않는다.
