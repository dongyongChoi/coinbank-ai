# ADR 006. 송금·가입 이벤트를 Kafka로 어떻게 빠짐없이 보낼 것인가

- 상태: 채택됨 (Spring Modulith 이벤트 발행 기록 + Kafka 외부 발행)
- 날짜: 2026-11-24

## 맥락
송금과 특판 가입이 끝나면 알림 모듈이 알 수 있게 이벤트를 Kafka로 보낸다. 알림은 M5에서 별도 서비스로 떼어 낼 예정이라 Kafka가 둘 사이의 약속이 된다.

DB에 기록하고 Kafka로 바로 보내면 둘이 어긋난다. 기록 뒤 보내기 전에 앱이 죽으면 송금은 됐는데 이벤트가 사라지고, 먼저 보내면 송금이 롤백돼도 이벤트는 나간다(이중 쓰기 문제). 목표는 "이벤트 유실 0건"이다.

## 선택지
### A. Outbox 테이블과 릴레이를 직접 만들기
`outbox_event` 테이블에 업무 기록과 같은 트랜잭션으로 이벤트를 적고, 주기적으로 꺼내 Kafka로 보내는 릴레이를 만든다.
- 장점: 언제 적히고 언제 나가는지, 실패하면 어떻게 되는지 모두 내 코드에 보인다.
- 단점: 다시 보내기, 순서, 정리를 직접 만들어야 한다.

### B. Spring Modulith 이벤트 발행 기록 + `@Externalized` (채택)
`ApplicationEventPublisher.publishEvent`로 발행하면 Modulith가 같은 트랜잭션에서 `event_publication`에 적는다. `@Externalized`가 붙은 이벤트는 커밋 뒤 다른 스레드가 Kafka로 보내고, 성공하면 `completion_date`를 적는다.
- 장점: 코드가 적다. 이미 쓰는 Modulith와 "모듈 간 호출은 공개 API나 이벤트로만" 규칙에 맞는다.
- 단점: 동작이 라이브러리 안에 있다. 기본 설정을 몰라 두 번 헤맸다(아래 "알려진 문제").

### 고르지 않은 것: 커밋 뒤 `KafkaTemplate`으로 바로 보내기
이중 쓰기 문제를 그대로 남긴다.

## 구성 (B)
- 보내는 쪽: 이벤트 `TransferCompleted`·`SubscriptionCreated`(`@Externalized("transfer-completed")` 등). Kafka 메시지 내용은 Modulith가 JSON 바이트로 바꾼다.
- 다시 보내기: `EventResubmission`이 10초마다 30초 넘게 완료 표시가 없는 이벤트를 다시 보낸다(`IncompleteEventPublications`). Kafka 프로듀서는 최대 10초만 기다린다(`delivery.timeout.ms`). 기준(30초)을 대기 시간(10초)보다 길게 둬서 보내는 중인 이벤트를 다시 보내는 일을 줄인다.
- 받는 쪽: 알림 모듈이 `processed_event`에 "토픽:업무 ID"를 `INSERT IGNORE`로 남기고 알림과 같은 트랜잭션에 둔다(멱등 컨슈머). 처음 붙는 그룹은 토픽의 처음부터 읽는다(`earliest`).
- 받는 쪽 실패: 1초부터 2배씩(최대 10초) 쉬며 5번 다시 시도하고, 그래도 안 되면 `{토픽}-dlt`로 옮긴다. 망가진 JSON은 바로 옮긴다.

결과적으로 "최소 한 번(at-least-once)" 전달이다. 같은 이벤트가 두 번 갈 수 있고, 받는 쪽이 한 번만 처리한다.

## 측정 결과
### 앱 강제 종료(kill -9)
조건: 계좌 100개, k6 가상 사용자 50명, 송금 5,000번 시도. 시작 5초 뒤 앱을 `kill -9`로 죽이고 3초 뒤 다시 켰다. 죽인 동안의 요청은 연결 실패로 끝나고 k6는 1초 쉬고 다음 송금으로 간다. 3번 쟀다.

| 회차 | 송금 | 기록된 이벤트 | kill 때 못 보낸 이벤트 | Kafka 메시지 | 알림이 된 이벤트 | 알림 | 못 보낸 이벤트(끝) | 잔액이 틀린 계좌 |
|---|---|---|---|---|---|---|---|---|
| 1 | 4,604 | 4,604 | 2,485 | 4,605 | 4,604 | 9,208 | 0 | 0 |
| 2 | 4,596 | 4,596 | 2,459 | 4,597 | 4,596 | 9,192 | 0 | 0 |
| 3 | 4,603 | 4,603 | 2,503 | 4,604 | 4,603 | 9,206 | 0 | 0 |

- 앱을 죽인 순간 이벤트의 약 97%가 아직 나가지 않은 상태였다. 다시 켠 뒤 `EventResubmission`이 모두 보냈다.
- Kafka에는 회차마다 송금보다 1건 더 쌓였다(다시 보내기가 만든 중복). 알림은 송금의 정확히 2배(출금·입금)라 중복이 걸러졌다.

### 부하 중 이벤트가 밀리는 정도 (kill 없음)
같은 조건으로 송금 5,000건을 9초 동안 보내고 2초마다 못 보낸 이벤트를 셌다. 송금이 끝나는 순간 4,453건이 밀려 있었고, 초당 약 450건씩 줄어 송금이 끝나고 11초 뒤에 0이 됐다. 부하가 걸리면 알림이 10초 넘게 늦을 수 있다. 보내는 스레드(기본 8개)와 DB 커넥션(10개)을 송금과 나눠 쓰기 때문으로 추정한다(확인하지 않음).

### Kafka가 대답하지 않을 때 (테스트)
`EventRecoveryTests`: Kafka 컨테이너를 멈춘 동안 송금은 2초 안에 끝나고, 이벤트는 미완료로 남았다가 Kafka를 풀면 다시 보내져 도착했다. 다시 보내기를 멈추면 도착하지 않았다.

## 결정
이벤트 발행은 Spring Modulith 이벤트 발행 기록과 `@Externalized`(B)로 하고, 주기적 다시 보내기와 멱등 컨슈머, DLT로 유실을 막는다.

## 결정 이유
(Claude Code가 측정 결과를 바탕으로 작성했다.)

목표는 "이벤트 유실 0건"이고, 그러려면 업무 기록과 이벤트 기록이 같은 트랜잭션에 들어가야 한다. A와 B 모두 이것을 만족한다. 차이는 다시 보내기와 완료 표시를 내가 만드느냐, 라이브러리가 하느냐다. 이 프로젝트는 이미 Spring Modulith로 모듈 경계를 검사하고 있고, 모듈끼리는 이벤트로 말한다는 규칙이 있다. B는 그 이벤트를 그대로 Kafka까지 보내므로 새 테이블·릴레이 코드 없이 같은 규칙 위에 선다.

측정으로 B가 목표를 지키는 것을 확인했다. 부하 중에 앱을 `kill -9`로 죽여 이벤트의 약 97%가 아직 나가지 않은 상태였는데도, 세 번 모두 다시 켠 뒤 모든 송금이 알림이 됐고 못 보낸 이벤트는 0건, 잔액이 틀린 계좌도 0개였다. 다시 보내기가 만든 중복(회차마다 1건)은 멱등 컨슈머가 걸러 알림이 정확히 송금의 2배였다.

B의 대가는 동작이 라이브러리 안에 숨어 있다는 점이다. 바이트 직렬화와 `varchar(255)`는 직접 찾기 전까지 보이지 않았다. 이것은 테스트(`EventPublicationTests`, `EventRecoveryTests`)와 아래 "알려진 문제"로 드러내 두고 감당하기로 했다. 알림을 M5에서 따로 떼어 내면 받는 쪽은 Kafka 메시지만 알면 되므로, 보내는 쪽을 A로 바꾸더라도 받는 쪽에는 영향이 없다.

## 알려진 문제
- `event_publication.serialized_event`가 `varchar(255)`다. Modulith의 JPA 엔티티가 길이를 정하지 않아 Hibernate(`ddl-auto: update`)가 기본값으로 만들었다. MySQL이 엄격 모드(`STRICT_TRANS_TABLES`)라, 이벤트 JSON이 255자를 넘으면 기록에 실패하고 같은 트랜잭션의 송금·가입도 실패할 것으로 예상한다(재현하지 않음). 지금 가장 긴 송금 이벤트는 145자다. 고치려면 스키마를 직접 관리해야 해서(Flyway 등) 나중으로 미룬다.
- Modulith는 Kafka 메시지 내용을 바이트로 바꾸고, 읽는 쪽 기본값도 바이트로 바꾼다(`kafka-json.properties`). 설정 파일에 보이지 않는다.
- Kafka가 없는 테스트에서 외부 발행을 켜 두면 없는 Kafka를 기다려 테스트 클래스마다 약 30초 늦어진다. `@IntegrationTest`에서 끄고 `@KafkaTest`에서 켠다.
- DLT로 옮긴 이벤트를 다시 넣는 도구가 없다.
- 앱이 여러 대가 되면 여러 대가 같은 미완료 이벤트를 동시에 다시 보낼 수 있다. 받는 쪽이 한 번만 처리하므로 알림이 틀리지는 않지만 Kafka 메시지는 늘어난다.

## 측정의 한계
- 앱, MySQL, Kafka, k6가 모두 한 컴퓨터에 있다. 조건마다 3번(밀림 측정은 1번) 쟀다.
- 앱이 보내는 도중 Kafka 브로커가 죽는 경우는 컨테이너 일시 정지(pause)로만 흉내 냈다.
