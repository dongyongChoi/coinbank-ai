# ADR 002. 모듈 경계를 무엇으로 강제할 것인가

- 상태: 채택됨
- 날짜: 2026-11-15

## 맥락
이 프로젝트는 모듈러 모놀리스로 시작해 M5에서 알림 모듈을 별도 서비스로 떼어낸다. 그때까지 모듈 사이가 뒤엉키지 않아야 분리가 가능하다. 프로젝트 원칙은 "모듈 경계는 코드로 강제한다. 모듈 간 호출은 공개 API나 이벤트로만 한다"이다.

모듈은 `account`, `transfer`, `product`, `notification`, `home` 다섯 개다.

## 선택지
### A. 패키지 규칙만 두고 리뷰로 지킨다
- 장점: 도구가 필요 없다.
- 단점: 혼자 하는 프로젝트라 리뷰어가 없다. 한 번 어기면 아무도 모른다.

### B. Gradle 멀티 모듈
모듈마다 Gradle 프로젝트를 나누고 의존을 `build.gradle.kts`에 선언한다.
- 장점: 허용하지 않은 의존은 컴파일 자체가 안 된다. 가장 단단하다.
- 단점: 빌드 설정이 늘어난다. 모듈 내부 타입을 숨기려면 `internal` 가시성이나 별도 api 모듈이 더 필요하다. M5의 분리 과정을 겪기 전에 미리 다 나눠 버리게 된다.

### C. Spring Modulith (한 Gradle 프로젝트, 패키지 = 모듈)
메인 패키지 바로 아래 패키지를 모듈로 보고, `ApplicationModules.verify()` 테스트로 경계를 검사한다.
- 장점: 설정이 가볍다. 하위 패키지(`internal`)는 자동으로 숨겨지고, `allowedDependencies`로 허용 의존을 선언한다. 이벤트 외부화 기능이 M5의 서비스 분리 경로와 이어진다.
- 단점: 컴파일이 아니라 테스트 시점에 잡힌다. 클래스 파일을 분석하므로 컴파일되지 않은 코드는 보지 못한다.

## 결정
C를 채택했다. `ModularityTests`가 경계를 검사하고 CI에서 매번 돈다.
- 공개 API는 모듈 패키지 바로 아래에 둔다 (`AccountService`, `AccountInfo`).
- 엔티티, 리포지토리, 컨트롤러는 `internal` 하위 패키지에 둔다.
- 허용 의존은 `ModuleMetadata.kt`에 선언한다 (`transfer` → `account`, `account` → 없음).

## 결정 이유
> 직접 작성: B(Gradle 멀티 모듈)가 아니라 C를 고른 이유를 본인의 말로.

## 확인한 것
- `transfer`가 `account.internal`의 타입을 쓰면 `verify()`가 실패한다.
- `transfer`가 허용 목록에 없는 `product`를 쓰면 `verify()`가 실패한다.
- `src/main/kotlin`에 둔 `.java` 파일은 컴파일되지 않아 검사에 잡히지 않았다. `src/main/java`로 옮기면 잡힌다.

## 후속
- M3: 모듈 간 이벤트를 도입하면서 `notification`의 허용 의존을 정한다.
- M5: 알림 모듈 분리 때 이 경계가 실제로 도움이 됐는지 회고한다.
